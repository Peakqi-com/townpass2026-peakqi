### 什麼會讓長輩願意下載、繼續用

1. **要先有「需要」，而且家人沒辦法輕易代勞。** 長輩沒用健保快易通的第一個原因是「沒有需要」，每百人有 40.4 人（例如「有需要就由其他人處理」）（S111 圖 8-9）。系統性回顧也把「需要」和「替代方案（由家人或配偶幫忙）」列為接受科技的因素（[Peek et al. 2014, IJMI](https://doi.org/10.1016/j.ijmedinf.2014.01.004)，納入 16 篇研究）。
2. **好處要立刻看得到。** 113 位長輩的焦點團體中，正面評價多於負面。正面評價多半是「能幫忙做事、方便、功能有用」，負面評價則是「反而添麻煩、功能沒用、擔心安全與可靠性」（[Mitzner et al. 2010, Computers in Human Behavior](https://doi.org/10.1016/j.chb.2010.06.020)）。
3. **家人是把 App 帶進門的人。** 長輩上網遇到問題，每百人有 65 人找子女；用過健保快易通的長輩，42.2% 是別人代為操作（S111）。美國 65 歲以上約四分之三表示「通常需要別人幫我設定或教我用」（48% 非常符合、25% 有點符合）（[Pew Research Center 2017](https://www.pewresearch.org/internet/2017/05/17/barriers-to-adoption-and-attitudes-towards-technology/)，引用 2015 年調查）。家人的影響也是接受科技的因素之一（Peek 2014）。臺北市長輩不用扶老修繕補助的原因之一是「需要家人決定」（T113）。
4. **信任與隱私是最大的門檻。** 美國 50 歲以上的人認為採用科技最大的障礙是資料隱私，其次是「搞不清楚到底值不值得」；每 5 人有 3 人覺得科技不是為他們這個年紀設計的（[AARP 2026 Tech Trends](https://www.aarp.org/pri/topics/technology/internet-media-devices/2026-technology-trends-older-adults/)，2025 年 9–10 月調查，3,838 人）。
5. **說明要白話，要讓長輩有信心。** 65–76 歲的平板新手（18 人）提到的障礙包括：說明太技術性、缺乏知識與信心、健康問題（關節炎、視力）。不過多數人「渴望學習」，66.6% 表示以後可能會繼續用（[Vaportzis et al. 2017, Frontiers in Psychology](https://doi.org/10.3389/fpsyg.2017.01687)）。
6. **會留下來的關鍵是「不出錯、有人接住」。** 健康類 App 的使用者在 100 天內流失的中位數是 70%，原因包括技術問題、隱私、體驗差、內容不符合需求（[Kidman et al. 2024, JMIR](https://doi.org/10.2196/56897)；對象是一般成人，不限長輩）。另一項研究訪問 55 位社區長輩，停用的原因是技術問題和缺乏社會支持（[Wong et al. 2024, BMC Nursing](https://doi.org/10.1186/s12912-024-01909-w)，摘要）。
7. **價格不是主因。** 只有 2.8% 的長輩會因為「免費吃到飽」而考慮上網（S111）。

### 建議調整（只是建議，不要求現在做）

**(1) 不建議換對象，也不建議擴大範圍。** 長輩和視障、聽障本來就大幅重疊：聽障者 76.3%、視障者 59.4% 年滿 65 歲（見 README §1）。前幾名的需求（健康、照顧、出門、打電話）三類人都有，所以應該把同一群人的少數幾個情境**做深**。決選配分中，服務完整度占 30、技術穩定度占 20，合計一半，做深比做廣有利。

### 1.12 淺白語言／易讀對理解的效果（全站用語）

這些研究支持全站用短句、常用字並配圖示，但效果有限：簡化文字能提高理解，卻不保證一定看懂，關鍵步驟還是要有人可以問。

### 證據缺口與矛盾

**互相矛盾的證據**
- **提醒到底有沒有用**：Bhargava 2015、Finkelstein 2019 說有用，Linos 2022 的 6 個實驗都沒有效果。Daigneault 2025 回顧後認為，「提供資訊」和「協助申請」比只發提醒有效。所以 M6／M12 不能只發提醒，要附上申請方法。
- **字級**：Darroch 2005 認為 6 點以上閱讀表現差異不大，建議 8–12 點；Yeh 2020 則發現 22 pt 長輩表現最好。兩者的裝置和單位不同，不能直接比較；本作品採用比較大的字。
- **易讀效果**：Sutherland 2016 回顧後認為證據有限，Buell 2020 隨機實驗中單獨簡化文字沒有顯著效果，Hurtado 2014 加圖也沒有比較好。淺白用語是必要的，但不夠。
- **語音**：Kim 2021 發現語音能降低長輩怕按錯的焦慮，Vipperla 2010、Cohn 2026 則顯示長者和失智者的辨識錯誤比較多。所以語音只能當其中一個選項。
- **家人代理**：Grošelj 2022 發現，代為上網的人從子孫轉向配偶；M7 假設「家人就是子女」，不一定成立。Tang 2022 也指出家人會從「保護」變成「監督」，設計上要顧及長輩的自主與隱私。
- **事前提醒會變弱**：Scheibe 2014 發現，提醒同一種詐騙的效果會隨時間降低，所以 M11 要在長輩接觸到可疑訊息時隨時能用，不能只靠一次宣導。

**只適用國外情境**
- 福利領取的實驗都在美國（EITC、SNAP），申請制度、寄信文化和臺灣不同。
- 共餐、社會參與的大型研究多在日本；臺灣的 Huang 2017 只在男性看到效果，而且全是觀察性研究，不能推論共餐「造成」健康改善。
- 視障者搭運輸（Azenkot 2011）是美國公車情境；臺灣只查到臺北市碩士論文（李森光 2012，5 人）。
- 易讀研究的對象是英國的智能障礙者，不是長輩。
- 詐騙盛行率（Burnes 2017）是美國資料；臺灣沒有查到長輩詐騙盛行率的同儕審查研究。

**查不到（證據缺口）**
- 「依需求而不是依機關」找服務的使用者測試研究：未查到（`accessibility-research.md` §6.1 已列，仍未補上）。
- 臺灣長輩用華語語音助理、長者華語語音辨識錯誤率的同儕審查研究：未查到（只有台語預印本）。
- 臺灣家人代理使用（proxy use）的研究：未查到。
- 臺灣福利 non-take-up 的本地研究：只查到失智長照（施姵宇 2017），沒有查到重陽禮金、敬老補助這類現金福利的研究。
- 119 簡訊報案、看診溝通卡的使用效果研究：未查到。
- 防詐工具說「很像〇〇詐騙」、不說「安全」這種回應方式的效果研究：未查到，目前是依 Scheibe 2014 推論。
- 淺白語言對長輩（而非智能障礙者）的效果研究，以及這個主張的頂刊或頂會論文：都未查到。
- 臺灣的 1.2 主張只有 Linders 2018（臺灣個案，但刊在國際期刊），沒有查到國內期刊或政府委託研究。

**驗證失敗或未列入**

- Wilpon & Jacobsen 1996（兒童與長者語音辨識，ICASSP）：記憶中的 DOI 實際指向另一篇論文（Eide, vocal tract length normalization），剔除。

### 2.5 引用官方文字的著作權判斷

**條文**（著作權法，111.06.15 修正，[J0070017](https://law.moj.gov.tw/LawClass/LawAll.aspx?pcode=J0070017)）
- 第 9 條：「憲法、法律、命令或公文」不得為著作權標的；「公文，包括公務員於職務上草擬之文告、講稿、新聞稿及其他文書」。
- 第 10-1 條：保護「僅及於該著作之表達，而不及於其所表達之思想、程序…操作方法、概念」。
- 第 50 條：「以中央或地方機關或公法人之名義公開發表之著作，在合理範圍內，得重製、公開播送或公開傳輸」。
- 第 64 條：依第 50 條利用時，「應明示其出處」。第 65 條則列出判斷合理使用的 4 項基準。

**機關自己的開放宣告**（比著作權法的條文更直接）
- 警政署〈政府網站資料開放宣告〉（113-07-17 更新）：「內政部警政署網站上刊載之所有資料與素材…採政府資料開放授權條款-第1版發布」，可以「重製、改作、編輯、公開傳輸」，「然使用時應註明出處」；但「經機關特別聲明須經同意方可使用者」不在宣告範圍內。[npa.gov.tw](https://www.npa.gov.tw/ch/app/artwebsite/view?module=artwebsite&id=895&serno=1057af14-0d7d-464c-836a-0856d014cc9a)
- 臺北市政府〈政府網站資料開放宣告〉：「本府網站上刊載之所有資料與素材」以「無償、非專屬、得再授權之方式提供公眾使用」，「然使用時，應註明出處」；同樣不包括特別聲明需要另外取得同意的資料。[gov.taipei](https://www.gov.taipei/News_Content.aspx?n=10FDEA7683714512&sms=AA987E1C50412097&s=3B6C92FD22C01611)

**結論**
1. **165 官方文章文字（M11）**：可以合法引用。主要依據是警政署的開放宣告（政府資料開放授權條款第 1 版，可以改作和再散布）；備位依據是著作權法第 50 條＋第 64 條。條件是每一筆都要註明出處（`antifraud.json` 已經附原文網址），並照授權條款附件的格式寫一段顯名聲明。
2. **消防局宣導單上的 119 簡訊格式（M8）**：格式、欄位順序和號碼屬於「操作方法」與事實，依第 10-1 條本來就不受保護；就算逐字照抄宣導單，也在臺北市政府開放宣告的範圍內。要註明出處（README §5 已經有）。
3. 第 9 條**不建議當主要依據**：宣導文章、宣導單是不是第 9 條第 2 項所說的「文告…其他文書」，條文沒有寫清楚。

**不確定的地方**
- 165 全民防騙網（165.npa.gov.tw）的頁尾沒有抓到自己的宣告。它是不是適用警政署主網站的宣告，或者有沒有「特別聲明須經同意」的內容，都要用瀏覽器確認。
- 消防局自己網站的宣告頁（tfd.gov.tw）打開是錯誤頁；目前是用市府總宣告推定。
- 依須知捌、一、(三)，AGPL 範圍外的資料要由隊伍擔保。建議在 README 寫明：`antifraud.json` 裡的官方文字依「政府資料開放授權條款第 1 版」授權，**不屬於 AGPL 的範圍**。

1. **README 授權段的 TODO 可以結案**：須知捌、一、(二) 已經附了原文（見 §2.1）。README 寫的「指引沒有附原文」只適用於工作坊投影片，不適用於須知。

### 3.2 AGPL-3.0 第 13 條與本作品

**條文**（本 repo `LICENSE` 第 540–551 行）：修改後的版本「must prominently offer all users interacting with it remotely through a computer network … an opportunity to receive the Corresponding Source」。GNU 的說明是「your server must also allow them to download the source code corresponding to the modified version running there」（[Why the Affero GPL](https://www.gnu.org/licenses/why-affero-gpl.html)）。

**是否適用**：GPL FAQ [#AGPLv3InteractingRemotely](https://www.gnu.org/licenses/gpl-faq.html#AGPLv3InteractingRemotely) 寫明，程式只要「expressly designed to accept user requests and send responses over a network」就算。本服務是城市通 WebView 載入的網頁，市民透過網路使用，所以適用。`LICENSE` 附錄（第 650–656 行）也建議網頁應用「display a "Source" link」。

**現況（只檢查，沒有改檔）**：
- `src/` 裡**沒有**給使用者看的原始碼連結。
- 唯一的 `github.com/Peakqi-com` 在 `src/lib/opendata/sources.ts:48`，是代理送給 data.taipei 的 `User-Agent` 標頭，使用者看不到。
- `src/data/services.json:221`、`:262` 的 `source` 指向本服務網址，不是原始碼。
- repo 是公開的（`gh api`：visibility public），README 第 8–9 行有連結，但 App 裡的使用者看不到 README。
- 嚴格說，§13 拘束的是「修改後提供服務的人」。隊伍是著作權人，不受自己的授權拘束；但資訊局整併、修改後就會觸發這條義務，所以現在就該先做好。

**建議**：
1. 在 `/mode`（選模式頁）或首頁最下方加一個看得到的「原始碼與授權（AGPL-3.0）」連結，用 `openLink()` 開 GitHub（WebView 不支援 `target="_blank"`）。連結要有可見文字，報讀軟體才念得到。
2. 連結指向「部署版本對應的程式碼」：可以連到 repo，同時在頁面上顯示版本號或 commit。
3. （選做）`GET /api/opendata` 回傳的 JSON 加一個 `source` 欄位，讓直接呼叫 API 的人也看得到原始碼位置。
4. README「授權」段寫明：Corresponding Source＝本 repo；App 端原始碼＝Peakqi-com/TownPass。

### 4.4 友善寫法清單

1. **重點放在標題和第一句**，不寫開場白（視障者常用 3～5 倍速、跳著聽）。依據：[Google 無障礙寫作](https://developers.google.com/style/accessibility)（key information first）；[W3C COGA](https://www.w3.org/TR/coga-usable/)〈Keep Text Succinct〉。
2. **標題可以跳讀**：一份文件一個 H1，層級不跳，標題本身就看得懂。依據：Google（Headings）；COGA 目標 2〈Help Users Find What They Need〉；城市通 ST1。現況 ✅。
3. **表格要有表頭**，表格前用一句話說明這張表是什麼，不合併儲存格。依據：Google（Tables）。現況：表頭 ✅；有些表格前沒有說明句 🔧。
4. **圖要有替代文字**，寫出圖的目的；裝飾圖用空的 alt；資訊不能只放在圖裡。依據：Google（Alt text）；城市通 AT1、AT2。
5. **ASCII 圖、emoji 要附文字**：報讀軟體可能會念出框線字元和 emoji 名稱，所以先給文字版；狀態寫「完成／未完成」，不要只靠符號或顏色。依據：Google（color and cues）。
6. **連結文字單獨看也懂**：不用「這裡」，也不用 ID 片段。依據：Google（Link text）。現況 🔧：§5 用「b02cd6b2…」當連結文字，建議改成資料集名稱。
7. **不用方位詞**，改用段落連結。依據：Google（directional language）。現況 🔧：第 31、43 行寫「見下方」。
8. **縮寫第一次出現就解釋**（TTS、CORS、TWD97、SSRF、WebView），或連到名詞小辭典。依據：Google（plain language）；SfPC 第 10 條；COGA〈Use Clear Words〉。
9. **一句一件事、步驟分開編號**；避免雙重否定，用字面意思。依據：COGA〈Separate Each Instruction〉〈Avoid Double Negatives or Nested Clauses〉〈Use Literal Language〉；Google 建議英文句子約 26 字內。
10. **引言框（`>`）只用來放引言**：報讀軟體會念出「引言」。依據：Google（semantic elements）；standard-readme（簡短描述不用 `>`）。現況 🔧：開頭三段都用了 `>`。
11. **中英文之間、中文和數字之間加空格**，用全形標點，專有名詞大小寫正確（GitHub、Node.js）。依據：[中文文案排版指北](https://github.com/sparanoid/chinese-copywriting-guidelines)（MIT）。現況 ✅：只有隊名「AI城市起風」沒加空格，這是專有名詞，可以保留。
12. **標示日期**：資料要有查證日期，README 要有最後更新日。依據：入門指引 p.38「透明：即時更新」；研究 Aghajani 2020（過時的文件）、Sholler（規則 4）。現況：資料 ✅；README 本身沒有日期 🔧。
13. **README 只當入口**：長篇參考資料（Handler 細節、研究）放到 `docs/` 再連過去，用相對連結。依據：Diátaxis；GitHub〈About READMEs〉。
14. **用語淺白、指引清楚**，用「可能可以申請」這種不過度承諾的說法。依據：入門指引 p.38「透明」；〈政府數位服務指引〉第十一條「遵循易用性原則」；SfPC 第 10 條（閱讀程度約國中）。

### 5.4 整合原則

1. **網頁端套件為什麼在 App 和 Web 都能跑**：5.1 和 5.2 的網頁端套件都是純 JavaScript，不是沒有依賴，就是依賴全為寬鬆授權。它們都不需要 Service Worker、WebGPU、Web Speech 或 WASM；用到的瀏覽器能力只有 DOM／Canvas（Leaflet）、WebGL（MapLibre，README 明寫支援 webview）、IndexedDB（idb-keyval）和 `Intl.Segmenter`，WKWebView 和 Android WebView 都有。城市通 WebView 不支援 `window.open`、`alert`，iOS 也不支援 `navigator.vibrate`，這些套件都用不到。不過 Leaflet 右下角授權標示裡的連結，在 WebView 裡點下去可能會直接跳離服務頁，建議改成透過 `open_external` 開啟（要實機確認）。
2. **斷網**：比對用的套件都打包進 JS bundle，跟著 README §3 的「預載 36 頁」一起進快取，斷網後照常能用。pinyin-pro、opencc-js 體積比較大，請直接在 `/find`、`/antifraud` 頁面靜態 import（Next.js 會依路由切分程式碼），讓預載時一起下載；不要用執行時才觸發的 dynamic import，否則斷網後如果之前沒載過，就會用不了。地圖圖磚不能預先下載（OSM 政策明文禁止；國土測繪中心也是線上 WMTS），所以維持 README §3 的「斷網後不能用：附近共餐上課、視障出門的即時資料」，改用文字清單代替。
3. **App 端能力的 Web 退路**（對照 README §3「長輩模式新增的 App Handler」）：

| Handler | App 內（WebView） | 一般瀏覽器的退路（`elder.ts` 的 mock） |
|---|---|---|
| `speak` | flutter_tts | 用 `speechSynthesis`，但只挑 `localService === true` 的聲音（網路聲音等於用雲端，不能用）；不支援就只顯示文字。Android WebView 沒有 Web Speech，所以 App 內一律走 Handler |
| `a11y_state` | 回報螢幕閱讀器狀態和字級 | 固定回 `{ screenReader: false, textScale: 1 }`，字級交給瀏覽器縮放 |
| `haptic` | 原生觸覺回饋 | 不做任何事（iOS 不支援 `navigator.vibrate`） |
| `open_external` | 交給外部 App 開啟 | 一般的 `tel:`／`sms:`／`https:` 連結 |
| `listen` | speech_to_text（`onDevice`）；手機不支援時回 `offline_unavailable`；可以加 5.2 的 Whisper 當備案 | **不要用**瀏覽器的 `SpeechRecognition`（MDN 說明 Chrome 會把音訊送到伺服器辨識，等於用雲端），改成打字或點選 |

4. **授權把關**：上線前先跑 `npx license-checker-rseidelsohn@5.0.1 --start . --production --onlyAllow …` 和 `npx @cyclonedx/cyclonedx-npm --omit dev`；App 端跑 `dart run dart_pubspec_licenses:generate`。查證日已在本 repo 實測，現有依賴裡不是 MIT／BSD／Apache 的授權如下（請隊伍確認要不要寫進 README §6 揭露）：

### 6.3 技術導入：比賽期間建議不加新套件

- 三條主線用現有的技術棧與 Handler 就能做深，新增依賴只會增加穩定度風險與授權清單的工作量。
- 真的要加地圖，用 Leaflet＋國土測繪中心圖資；不要用 react-leaflet（Hippocratic 授權，見 §5.3）。
- 裝置端 LLM（flutter_edge_ai＋Gemma 4 E2B）可行，但 Android 要 minSdk 30、模型檔有數 GB，評審還可能在斷網下驗證。比照主持人的建議「沒有 AI 功能也能做出好作品」，先不加。

### 6.4 讓「真的有幫助」有證據

- 每條主線至少找 3 位真實使用者（長輩、視障者、聽障者，或他們的家人）實際走一次，記下卡在哪一步。這些紀錄就是決選問答時「民眾有感」最直接的證據。
- 實機開 VoiceOver、TalkBack、飛航模式，三條主線各完整測一次（README 目前標示尚未實測）。

### 6.5 待確認清單

- App fork 的授權（GPL-3.0 或 AGPL-3.0），見 §6.2。
- 黃燈授權（ISC 22 個、0BSD、CC0、BlueOak 等）：寬鬆授權但不在字面白名單，要由隊長決定是否接受，並在 README 註明。
- 資安清單判斷：pinyin-pro 的作者在北京（套件本身是 MIT）；sherpa_onnx 的中文模型（Paraformer、SenseVoice）屬於大陸廠牌，不要用。
